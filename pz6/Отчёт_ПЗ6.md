# Практическое занятие № 6. Защита данных на уровне таблиц, строк и представлений

Цель: научиться разграничивать доступ к данным в PostgreSQL на уровне таблиц, столбцов, строк и представлений по принципу минимальных привилегий.

Среда: PostgreSQL 16 в Docker, клиент psql.

## 1. Подготовка базы

```sql
CREATE TABLE students (
    id SERIAL PRIMARY KEY,
    full_name VARCHAR(100) NOT NULL,
    group_name VARCHAR(50) NOT NULL,
    email VARCHAR(100),
    scholarship NUMERIC(10,2)
);

CREATE TABLE grades (
    id SERIAL PRIMARY KEY,
    student_id INT NOT NULL REFERENCES students(id),
    teacher_username TEXT NOT NULL,
    subject VARCHAR(100) NOT NULL,
    grade INT NOT NULL CHECK (grade BETWEEN 0 AND 100)
);

INSERT INTO students (full_name, group_name, email, scholarship) VALUES
    ('Иван Петров', 'IT-21', 'ivan@example.com', 25000),
    ('Анна Садыкова', 'IT-22', 'anna@example.com', 30000),
    ('Данияр Ахметов', 'IT-21', 'daniyar@example.com', 20000),
    ('Мария Иванова', 'IT-23', 'maria@example.com', 28000);

INSERT INTO grades (student_id, teacher_username, subject, grade) VALUES
    (1, 'teacher01', 'Базы данных', 90),
    (2, 'teacher01', 'Базы данных', 85),
    (3, 'teacher02', 'Компьютерные сети', 92),
    (4, 'teacher02', 'Компьютерные сети', 88);
```

SELECT * FROM students и SELECT * FROM grades показали по 4 строки.

Вопрос: какие данные конфиденциальны? scholarship — финансовые сведения, нужны только бухгалтерии. email — контактные персональные данные, утечка ведёт к спаму и фишингу. full_name в связке с ними — персональные данные. id и group_name сами по себе не чувствительны.

## 2. Права на таблицы и столбцы

```sql
CREATE ROLE teacher_limited;
CREATE ROLE accountant_limited;
GRANT SELECT (id, full_name, group_name) ON students TO teacher_limited;
GRANT SELECT (id, scholarship) ON students TO accountant_limited;
```

Проверка через SET ROLE:

- Преподаватель читает ФИО — ожидалось разрешено — получил 4 строки
- Преподаватель читает стипендию — ожидалось запрещено — получил permission denied for table students
- Бухгалтер читает стипендию — ожидалось разрешено — получил 4 строки
- Преподаватель изменяет стипендию — ожидалось запрещено — получил permission denied for table students

Право на столбец не даёт ни других столбцов, ни UPDATE/DELETE на таблицу.

## 3. Представление VIEW

```sql
CREATE VIEW student_public_info AS
SELECT id, full_name, group_name FROM students;

GRANT SELECT ON student_public_info TO teacher_limited;
REVOKE SELECT ON students FROM teacher_limited;
```

Под teacher_limited: SELECT * FROM student_public_info — 3 столбца, 4 строки. SELECT * FROM students — permission denied.

Замечание: REVOKE SELECT ON students снимает и столбцовые права, пришлось заново выдать GRANT SELECT (id, full_name, group_name). После отзыва нужно перепроверять все пути доступа.

Ответы на вопросы:

1. VIEW скрывает email и scholarship — их нет в запросе представления.
2. VIEW имеет свои права, таблица — свои. Если у роли остался прямой SELECT на students, она прочитает скрытые столбцы в обход VIEW. Нужно ещё и закрыть доступ к таблице.
3. VIEW удобнее, когда надо отдать только часть столбцов или строк, данные из нескольких таблиц одним объектом, или один срез многим ролям сразу.

## 4. Row-Level Security

```sql
CREATE ROLE teacher01 LOGIN PASSWORD 'Teacher01_Strong!';
CREATE ROLE teacher02 LOGIN PASSWORD 'Teacher02_Strong!';
CREATE ROLE teacher_rls_role;
GRANT teacher_rls_role TO teacher01;
GRANT teacher_rls_role TO teacher02;
GRANT SELECT, UPDATE ON grades TO teacher_rls_role;

ALTER TABLE grades ENABLE ROW LEVEL SECURITY;

CREATE POLICY grades_select_policy ON grades
    FOR SELECT TO teacher_rls_role
    USING (teacher_username = current_user);

CREATE POLICY grades_update_policy ON grades
    FOR UPDATE TO teacher_rls_role
    USING (teacher_username = current_user)
    WITH CHECK (teacher_username = current_user);
```

USING фильтрует видимые строки, WITH CHECK не даёт записать строку с чужим teacher_username.

## 5. Проверки

Подключился как teacher01 (\c postgres teacher01):

```sql
SELECT * FROM grades;                          -- 2 строки, id 1 и 2
UPDATE grades SET grade = 95 WHERE id = 1;     -- UPDATE 1
UPDATE grades SET grade = 100 WHERE id = 3;    -- UPDATE 0, чужая строка невидима
UPDATE grades SET teacher_username = 'teacher02' WHERE id = 1;
   -- ERROR: new row violates row-level security policy
```

Подключился как teacher02: SELECT * FROM grades — 2 строки, id 3 и 4, оценка id 3 осталась 92.

SET ROLE teacher_limited: SELECT scholarship — permission denied. SELECT * FROM student_public_info — 4 строки, 3 столбца.

Итог:

- Чтение разрешённых столбцов — разрешено — 4 строки
- Чтение стипендии преподавателем — запрещено — permission denied
- Чтение через VIEW — разрешено — 3 столбца, 4 строки
- Чтение оценок teacher01 — только свои — 2 строки
- Чтение оценок teacher02 — только свои — 2 строки
- Изменение чужой оценки — не изменяется — UPDATE 0

## Вывод

Использовал четыре механизма: GRANT/REVOKE на таблицы закрывают доступ к объекту целиком; столбцовые GRANT прячут финансовые и контактные поля от тех, кому они не нужны; VIEW даёт безопасный срез таблицы без прямого доступа к ней; RLS с USING/WITH CHECK — каждый преподаватель видит и меняет только свои строки и не может присвоить чужие.

Главное: создать пользователей и роли мало. Надо явно задать, какие таблицы, столбцы и строки доступны каждой роли, закрыть обходные пути (прямой доступ, наследование ролей, PUBLIC) и проверить под реальными учётками, что запреты действительно срабатывают.

# Практическое занятие № 7. Защита от SQL-инъекций

Цель: разобрать, почему конкатенация пользовательского ввода с SQL создаёт уязвимость, реализовать безопасный параметризованный запрос на Python с psycopg, добавить проверку формата ввода и определить дополнительные меры защиты.

Среда: PostgreSQL 16 в Docker, база university, Python 3 + psycopg.

## Этап 1. Учебная база

```sql
CREATE TABLE app_users (
    id SERIAL PRIMARY KEY,
    username VARCHAR(50) NOT NULL UNIQUE,
    full_name VARCHAR(100) NOT NULL
);

INSERT INTO app_users (username, full_name) VALUES
    ('student01', 'Иван Петров'),
    ('student02', 'Анна Сидорова'),
    ('teacher01', 'Мария Иванова');

SELECT id, username, full_name FROM app_users;
```

Результат: 3 строки (student01, student02, teacher01).

## Этап 2. Небезопасный запрос

```python
username = input("Введите логин: ")
query = (
    "SELECT id, username FROM app_users "
    + "WHERE username = '" + username + "'"
)
print(query)
```

Скрипт только печатает текст, к базе не подключается. Что получилось при разных вводах:

- student01 → WHERE username = 'student01'
- student'01 → WHERE username = 'student'01' — синтаксис сломан, запрос упадёт
- ' OR '1'='1 → WHERE username = '' OR '1'='1' — условие всегда истинно, вернёт всех пользователей
- x'; DROP TABLE app_users; -- → WHERE username = 'x'; DROP TABLE app_users; --' — вторая команда удалит таблицу

Ответы на вопросы:

1. Почему конкатенация опасна. Введённая строка вклеивается в текст команды и парсер СУБД не отличает, где кончился запрос программиста и начались данные пользователя. Апостроф закрывает строковый литерал, и всё после него читается как SQL.

2. Какая часть должна оставаться неизменной. Структура запроса: SELECT id, username FROM app_users WHERE username = ?. Меняться должно только значение, подставляемое на место параметра.

3. Почему проверка длины не спасает. Вредоносная строка может быть короткой: ' OR '1'='1 это 11 символов, x'; DROP TABLE app_users;-- тоже укладывается в 30. Длина ничего не говорит о содержимом.

4. Безопасный способ. Параметризованный запрос: cursor.execute("... WHERE username = %s", (username,)). Текст команды и значение уходят в СУБД раздельно, значение никогда не интерпретируется как SQL.

## Этап 3. Безопасный запрос

```python
import os
import psycopg

username = input("Введите логин: ")
connection_string = os.environ["DATABASE_URL"]

with psycopg.connect(connection_string) as conn:
    with conn.cursor() as cursor:
        cursor.execute(
            "SELECT id, username, full_name FROM app_users WHERE username = %s",
            (username,),
        )
        rows = cursor.fetchall()
        if rows:
            for row in rows:
                print(row)
        else:
            print("Пользователь не найден")
```

Строка подключения берётся из переменной окружения DATABASE_URL, пароль в коде не хранится.

Фактические результаты:

- student01 → (1, 'student01', 'Иван Петров')
- teacher01 → (3, 'teacher01', 'Мария Иванова')
- nobody → Пользователь не найден
- student'01 → Пользователь не найден
- ' OR '1'='1 → Пользователь не найден

Апостроф и конструкция OR '1'='1 ушли в базу как обычное значение параметра: СУБД искала пользователя с логином буквально student'01 и не нашла. Инъекция не сработала.

## Этап 5. Дополнительные меры защиты

Проблема — мера:

- SQL формируется конкатенацией строк — параметризованные запросы (%s в psycopg), ORM. Структура запроса фиксирована, данные передаются отдельно.
- Приложение подключается с правами администратора — отдельный пользователь app_user с минимальными правами. В работе ему выдан только SELECT на app_users. Попытка DELETE под ним: ERROR: permission denied for table app_users. Даже если инъекция пройдёт, удалить или изменить данные не получится.
- Пароль БД записан в коде — хранить в переменной окружения DATABASE_URL или в секрет-хранилище, не коммитить в репозиторий.
- Пользователь видит подробную ошибку SQL — перехватывать исключения, показывать общее сообщение, детали писать в лог. Текст ошибки раскрывает структуру таблиц и помогает подбирать инъекцию.
- Ввод не проверяется на формат — валидация по белому списку (регулярка), проверка длины и типа до выполнения запроса.

## Вывод

Конкатенация делает ввод пользователя частью SQL-команды, и один апостроф меняет логику запроса вплоть до удаления таблицы. Параметризованный запрос решает проблему на корню: значение никогда не парсится как SQL, что подтвердили проверки с student'01 и ' OR '1'='1. Проверка формата, минимальные права пользователя приложения, секреты вне кода и скрытие ошибок не заменяют параметризацию, но ограничивают ущерб, если где-то ошиблись.

# Практическое занятие № 5. Модель ролевого управления доступом RBAC

Цель: спроектировать и реализовать ролевую модель доступа RBAC в базе данных университета: создать роли, назначить им права, связать пользователей с ролями, построить иерархию ролей и проверить, что модель работает.

Среда: PostgreSQL 16 в Docker, база university, клиент psql.

## Исходная модель RBAC

Пользователь → Роль → Права → Ресурс

Например: teacher01 → teacher_role → SELECT students, teachers, groups; SELECT/INSERT/UPDATE grades.

В системе 500 студентов, 50 преподавателей, 10 бухгалтеров, 5 сотрудников деканата, 3 аналитика, 2 администратора. Выдавать права каждому из 570 человек отдельно нереально, поэтому права вешаются на 6 ролей.

## Задание 1. Проектирование

Роль — назначение — ресурсы

- student_role — работа со своими учебными данными — students, grades
- teacher_role — работа с учебным процессом — students, teachers, groups, grades
- accountant_role — работа с оплатами — payments
- dean_role — работа с учебной информацией — students, teachers, groups, grades, reports
- analyst_role — анализ данных — students, grades, payments, reports
- admin_role — администрирование — все объекты

## Задание 2. Создание ролей

```sql
CREATE ROLE student_role;
CREATE ROLE teacher_role;
CREATE ROLE accountant_role;
CREATE ROLE dean_role;
CREATE ROLE analyst_role;
CREATE ROLE admin_role;
```

Проверил через \du и SELECT rolname FROM pg_roles — все 6 ролей есть, у всех Cannot login (это групповые роли, не учётки).

Дополнительно создал пользователей student01, teacher01, accountant01, dean01, analyst01 с паролями.

## Задание 3. Права ролям

```sql
GRANT SELECT ON students, grades TO student_role;

GRANT SELECT ON students, teachers, groups TO teacher_role;
GRANT SELECT, INSERT, UPDATE ON grades TO teacher_role;

GRANT SELECT, INSERT, UPDATE ON payments TO accountant_role;

GRANT SELECT ON students, teachers, groups TO dean_role;
GRANT SELECT, INSERT, UPDATE ON grades, reports TO dean_role;

GRANT SELECT ON students, grades, payments, reports TO analyst_role;

GRANT ALL ON ALL TABLES IN SCHEMA public TO admin_role;
```

Замечание: INSERT в таблицу с SERIAL упал с ошибкой permission denied for sequence reports_id_seq. Ролям с INSERT пришлось дополнительно выдать GRANT USAGE ON SEQUENCE. Права на таблицу не включают права на её последовательность.

## Задание 4. Назначение ролей пользователям

```sql
GRANT student_role TO student01;
GRANT teacher_role TO teacher01;
GRANT accountant_role TO accountant01;
GRANT dean_role TO dean01;
GRANT analyst_role TO analyst01;
```

Ни одному пользователю права напрямую не выдавались, всё только через роли.

## Задание 5. Иерархия ролей

```sql
CREATE ROLE employee_role;
GRANT SELECT ON students TO employee_role;

CREATE ROLE senior_employee_role;
GRANT employee_role TO senior_employee_role;
GRANT SELECT ON teachers, groups TO senior_employee_role;
```

senior_employee_role → employee_role → SELECT students

Проверил через SET ROLE:

- senior_employee_role: SELECT students — разрешено (унаследовано), SELECT teachers — разрешено (своё), SELECT payments — permission denied
- employee_role: SELECT students — разрешено, SELECT teachers — permission denied

Старшая роль получила права базовой плюс свои.

## Задание 6. Разделение обязанностей

Роль 1 — Роль 2 — можно ли совмещать — почему

- Accountant — Administrator — нет — один человек может изменить платежи, поправить себе права и стереть следы. Классический конфликт интересов.
- Teacher — Student — нет — преподаватель-студент сможет видеть и менять собственные оценки.
- Analyst — Accountant — нежелательно — аналитик должен только читать; с ролью бухгалтера он сможет править платежи, которые сам же анализирует, отчёты станут недостоверными.
- Dean — Teacher — допустимо с оговоркой — права почти совпадают (деканат шире), конфликта нет. Но если сотрудник деканата ещё и ведёт предмет, лучше контролировать, чтобы он не правил оценки по своему предмету через dean_role.

Самая опасная пара: Accountant + Administrator.

## Задание 7. Проверка прав

Подключился под каждым пользователем:

- student01: SELECT students — разрешено. UPDATE students — permission denied for table students. UPDATE grades — permission denied for table grades.
- teacher01: SELECT students — разрешено. UPDATE grades SET grade = 90 — UPDATE 1. DELETE FROM grades — permission denied for table grades. SELECT payments — permission denied for table payments.
- accountant01: SELECT payments — разрешено. UPDATE payments — UPDATE 1. UPDATE grades — permission denied for table grades.
- dean01: SELECT reports — разрешено. INSERT INTO reports — INSERT 0 1. SELECT payments — permission denied for table payments.
- analyst01: SELECT payments — разрешено. UPDATE payments SET amount = 0 — permission denied for table payments. DELETE FROM students — permission denied for table students.

Разрешено: SELECT у всех по своим таблицам, UPDATE grades у преподавателя, UPDATE payments у бухгалтера, INSERT reports у деканата.

Запрещено: любой UPDATE/DELETE у студента и аналитика, DELETE grades у преподавателя, доступ к payments у преподавателя и деканата, доступ к grades у бухгалтера.

## Итоговая матрица RBAC

Роль — students — teachers — groups — grades — payments — reports

- Student — R — нет — нет — R — нет — нет
- Teacher — R — R — R — R/I/U — нет — нет
- Accountant — нет — нет — нет — нет — R/I/U — нет
- Dean — R — R — R — R/I/U — нет — R/I/U
- Analyst — R — нет — нет — R — R — R
- Administrator — полный доступ ко всем таблицам

Совпадает с выводом запроса к information_schema.role_table_grants.

## Вывод

Как RBAC упрощает управление безопасностью базы данных?

Права настраиваются один раз на роль, а не 570 раз на каждого пользователя. Новый преподаватель получает всё нужное одной командой GRANT teacher_role. Если преподавателям понадобилось новое право, оно выдаётся роли и сразу действует для всех 50. Увольнение — REVOKE роли, права исчезают разом. Иерархия ролей убирает дублирование: общие права лежат в базовой роли, специфичные в наследниках. Разделение обязанностей проверяется на уровне ролей: достаточно запретить совмещать Accountant и Administrator, не разбираясь в правах каждого человека. Модель легко проверить: матрица роль × таблица читается целиком из information_schema.

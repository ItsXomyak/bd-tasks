# Практическое занятие № 4. Авторизация и разграничение прав доступа в СУБД

Цель: научиться выдавать и отзывать права доступа через GRANT и REVOKE, объединять права в роли и проверять принцип минимальных привилегий.

Среда: PostgreSQL 16 в Docker, база university, клиент psql.

## Подготовка

Создал четыре таблицы: students, teachers, grades, payments. Добавил 3 студентов, 2 преподавателей, 3 оценки и 2 платежа.

## Задание 1. Пользователи

```sql
CREATE USER student_user WITH PASSWORD 'Student_123!';
CREATE USER teacher_user WITH PASSWORD 'Teacher_123!';
CREATE USER accountant_user WITH PASSWORD 'Accountant_123!';
CREATE USER db_admin WITH PASSWORD 'Admin_123!';
```

- student_user — студент
- teacher_user — преподаватель
- accountant_user — бухгалтер
- db_admin — администратор

## Задание 2. Матрица доступа

Роль — students — teachers — grades — payments

- Student — R — нет — R — нет
- Teacher — R — R — R/U — нет
- Accountant — нет — нет — нет — R/U
- Admin — R/C/U/D — R/C/U/D — R/C/U/D — R/C/U/D

Студенту достаточно видеть себя и оценки. Преподавателю нужно видеть студентов, коллег и менять оценки. Бухгалтер работает только с платежами. Администратор делает всё.

## Задание 3. GRANT

```sql
GRANT SELECT ON students, grades TO student_user;

GRANT SELECT ON students, teachers, grades TO teacher_user;
GRANT UPDATE ON grades TO teacher_user;

GRANT SELECT, UPDATE ON payments TO accountant_user;

GRANT ALL ON ALL TABLES IN SCHEMA public TO db_admin;
```

Проверка:

- student_user: SELECT students и grades — разрешено. UPDATE grades — ERROR: permission denied for table grades. У студента нет права UPDATE.
- teacher_user: SELECT grades — разрешено. UPDATE grades SET grade = 95 — UPDATE 1. DELETE FROM grades — permission denied for table grades.
- accountant_user: SELECT payments — разрешено. UPDATE payments — UPDATE 1. SELECT students — permission denied for table students.

## Задание 4. REVOKE

```sql
GRANT DELETE ON grades TO teacher_user;
-- под teacher_user: DELETE FROM grades WHERE id = 3  →  DELETE 1
REVOKE DELETE ON grades FROM teacher_user;
-- под teacher_user: DELETE FROM grades WHERE id = 1  →  permission denied for table grades
```

После GRANT DELETE преподаватель удалил строку, после REVOKE удаление снова запрещено.

## Задание 5. Роли

```sql
CREATE ROLE student_role;
CREATE ROLE teacher_role;
CREATE ROLE accountant_role;

GRANT SELECT ON students, grades TO student_role;
GRANT student_role TO student_user;

GRANT SELECT ON students, teachers, grades TO teacher_role;
GRANT UPDATE ON grades TO teacher_role;
GRANT teacher_role TO teacher_user;

GRANT SELECT, UPDATE ON payments TO accountant_role;
GRANT accountant_role TO accountant_user;
```

Теперь права лежат на ролях, а пользователи получают их через членство: student_user → student_role → SELECT students, grades. Проверил через information_schema.role_table_grants, права у ролей совпадают с матрицей.

## Задание 6. Минимальные привилегии

Под teacher_user:

- DELETE FROM students — ERROR: permission denied for table students
- DROP TABLE students — ERROR: must be owner of table students
- CREATE USER test_user — ERROR: permission denied to create role

Вывод: teacher_user имеет рабочие права, но не имеет административных.

## Задание 7. Аналитик

```sql
CREATE ROLE analyst_role;
GRANT SELECT ON students, grades, payments TO analyst_role;
CREATE USER analyst_user WITH PASSWORD 'Analyst_123!';
GRANT analyst_role TO analyst_user;
```

Под analyst_user: SELECT students и payments — разрешено. UPDATE students SET group_name = 'IT-25' — permission denied for table students.

## Итоговая проверка

Пользователь — SELECT — INSERT — UPDATE — DELETE

- student_user — да — нет — нет — нет
- teacher_user — да — нет — да (grades) — нет
- accountant_user — да (payments) — нет — да (payments) — нет
- analyst_user — да — нет — нет — нет
- db_admin — да — да — да — да

INSERT проверил у всех четырёх ограниченных пользователей — везде permission denied. db_admin выполнил INSERT, UPDATE, DELETE на students.

Ошибки СУБД, которые встретились:

- permission denied for table ... — нет права на операцию
- must be owner of table students — DROP может только владелец
- permission denied to create role — нет атрибута CREATEROLE

## Вывод

GRANT выдаёт права, REVOKE забирает, и СУБД реально отказывает в операциях без права. Роли позволяют настроить права один раз и раздавать их пользователям через членство, вместо повторения GRANT для каждого. Каждый пользователь получил ровно то, что нужно для работы: студент и аналитик только читают, преподаватель меняет оценки, бухгалтер меняет платежи, админ может всё.

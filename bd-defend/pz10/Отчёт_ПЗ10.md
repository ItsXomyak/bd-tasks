# Практическая работа № 10. Создание резервной копии БД и восстановление из Backup. Разработка стратегии резервного копирования

Цель: получить навыки создания резервных копий PostgreSQL, восстановления из них, проверки целостности и разработки стратегии резервного копирования.

Среда: PostgreSQL 16 в Docker, утилиты pg_dump, pg_restore, pg_dumpall, psql внутри контейнера. Копии сохраняются в каталог backups/.

## Задание 2. Создание резервной копии

```bash
pg_dump -U postgres -d university_backup -F c -f university_backup.dump
pg_restore -l university_backup.dump
pg_dump -U postgres -d university_backup -F p -f university_backup.sql
```

Результат:

- university_backup.dump — 5703 байт, custom-формат, сжатие gzip, заголовок файла PGDMP
- university_backup.sql — 4482 байт, обычный текст
- pg_restore -l показал 19 записей оглавления: таблицы students и grades, две последовательности, данные таблиц (TABLE DATA), первичные ключи и внешний ключ grades_student_id_fkey

Ответы на вопросы:

1. Отличие .dump и .sql. Файл .dump (формат custom) бинарный, сжатый, содержит оглавление объектов, позволяет восстанавливать выборочно и параллельно, читается только pg_restore. Файл .sql это обычный текст с командами CREATE TABLE, COPY и т.д., его можно открыть, править и выполнить через psql.
2. pg_restore работает с форматами custom (-F c), directory (-F d) и tar (-F t). Plain SQL восстанавливается через psql.
3. Если копия лежит на том же сервере, она погибнет вместе с базой при отказе диска, пожаре, шифровальщике или ошибке администратора. Копия на отдельном носителе или в другом месте переживает сбой основного сервера.
4. В дампе все данные в открытом виде: персональные данные студентов, email, оценки, при pg_dumpall ещё и хэши паролей ролей. Получив файл, злоумышленник получает всю базу без необходимости взламывать сервер. Копию нужно защищать так же строго, как саму базу.

## Задание 3. Восстановление из резервной копии

```bash
createdb -U postgres university_restore
pg_restore -U postgres -d university_restore university_backup.dump
```

```sql
\c university_restore
SELECT COUNT(*) FROM students;
SELECT COUNT(*) FROM grades;
SELECT s.full_name, s.group_name, g.subject, g.grade
FROM students AS s JOIN grades AS g ON s.student_id = g.student_id;
```

Количество оценок             | 5           | 5

Наличие таблицы grades        | есть        | есть

Вопрос: можно ли считать восстановление успешным, если файл Backup существует, но данные из него невозможно восстановить?

Нет. Резервная копия имеет ценность только как возможность вернуть данные. Файл, который не восстанавливается (повреждён, сделан несовместимой версией, неполный, нет ключа шифрования), равносилен отсутствию копии, при этом создаёт ложное чувство защищённости. Поэтому результат резервного копирования это успешно проверенное восстановление, а не наличие файла. Отсюда требование регулярно тестировать восстановление.

## Задание 4. Анализ способов резервного копирования

```
Критерий                        | pg_dump                          | pg_dumpall                              | pg_basebackup
Тип резервирования              | логическое                       | логическое                              | физическое
Что сохраняется                 | одна БД: схема и данные          | весь кластер: все БД, роли, табличные   | копия каталога данных кластера
                                | (SQL или архив)                  | пространства, только в SQL              | (файлы) + WAL
Для чего используется           | регулярные копии отдельной БД,   | полный перенос кластера, сохранение     | база для PITR, создание реплик,
                                | перенос, миграция между версиями | глобальных объектов (ролей)             | быстрое восстановление больших БД
Восстановление отдельных        | да (custom/directory: -t, -n,    | нет, только весь файл целиком           | нет, восстанавливается весь кластер
объектов                        | pg_restore -l / -L)              | (можно вырезать вручную из SQL)         |
Особенности                     | медленно на больших объёмах,     | тот же pg_dump по каждой БД + роли;     | нужна роль с REPLICATION, та же
                                | согласованный снимок, можно      | большой файл, нет сжатия custom         | мажорная версия и платформа,
                                | восстановить на другую версию    |                                         | сервер не должен быть запущен
                                |                                  |                                         | на восстановленном каталоге
```

Вывод. Для небольшой базы университета для регулярного копирования выбрал бы pg_dump в формате custom. База маленькая, дамп занимает секунды, файл сжат, можно восстановить отдельную таблицу, можно перенести на другую версию PostgreSQL, восстановление в отдельную базу тривиально. Раз в сутки дополнительно pg_dumpall --globals-only, чтобы сохранить роли. pg_basebackup и архив WAL добавлять только когда появится требование RPO меньше интервала дампа.

## Задание 5. Стратегия резервного копирования

### Шаг 1. Периодичность

```
Вид копирования               | Периодичность                      | Назначение
Полная логическая (pg_dump -F c) | ежедневно в 02:00                | восстановление БД целиком или отдельных таблиц
Копия ролей (pg_dumpall --globals-only) | ежедневно вместе с дампом | восстановление пользователей и прав
Физическая базовая (pg_basebackup) | еженедельно (воскресенье)      | основа для PITR
Архивирование WAL               | постоянно, archive_timeout = 15 мин | восстановление на момент времени
Проверка восстановления         | еженедельно автоматически, ежемесячно вручную | контроль пригодности копий
```

Что изменил относительно примера и почему:

- ежедневный pg_dump оставил, но добавил pg_dumpall --globals-only, иначе после восстановления на новом сервере не будет ролей
- вместо абстрактной дополнительной копии ввёл еженедельный pg_basebackup, так как без физической базовой копии архив WAL бесполезен
- для WAL задал archive_timeout = 15 минут, чтобы при малой нагрузке сегмент не ждал заполнения и RPO в 1 час точно выполнялся
- проверку восстановления сделал еженедельной автоматической (скрипт restore в тестовую базу + COUNT по таблицам), ежемесячной только ручную полную репетицию

### Шаг 2. Правило 3-2-1

1. Основная база — сервер PostgreSQL университета (диск сервера, экземпляр 1).
2. Первая резервная копия — сетевое хранилище (NAS) в серверной университета, отдельная система хранения (экземпляр 2, носитель 2). Туда пишутся ежедневные дампы, базовые копии и WAL.
3. Вторая резервная копия — удалённое объектное хранилище (S3-совместимое облако или дата-центр в другом здании), копия зашифрована, включён режим неизменяемости (object lock) на 30 дней (экземпляр 3, вне площадки).

Схема:

Сервер PostgreSQL → (pg_dump, pg_basebackup, archive_command) → NAS в серверной → (ежедневная синхронизация, шифрование) → удалённое хранилище

Срок хранения: ежедневные дампы 30 дней, еженедельные 3 месяца, копии на конец семестра 5 лет.

### Шаг 3. RPO и RTO

RPO = 1 час. RTO = 3 часа.

1. RPO (Recovery Point Objective) 1 час означает, что при сбое допустимо потерять не более одного часа последних изменений: должна существовать копия, отстающая от момента сбоя не больше чем на час.
2. RTO (Recovery Time Objective) 3 часа означает, что с момента сбоя до возобновления работы системы должно пройти не более трёх часов, включая обнаружение, восстановление и проверку.
3. Ежедневного pg_dump недостаточно: при сбое в 23:00 будут потеряны изменения за 21 час с момента ночного дампа. Ежедневный дамп даёт RPO около 24 часов.
4. Для RPO в 1 час нужно непрерывное архивирование WAL (wal_level = replica, archive_mode = on, archive_command, archive_timeout не больше 1 часа, лучше 15 минут) поверх еженедельного pg_basebackup, это даёт PITR на любой момент. Дополнительно потоковая репликация на standby-сервер (RPO близок к нулю, а при промоушене реплики RTO минуты). Обязателен мониторинг отставания архивации (pg_stat_archiver, failed_count) и контроль целостности переданных сегментов.

### Шаг 4. Защита резервных копий

1. Шифрование копий (pg_dump | gpg или шифрование на стороне хранилища), ключи хранятся отдельно от копий, в менеджере секретов.
2. Отдельная учётная запись backup_user с правами только на чтение (pg_read_all_data) и REPLICATION для pg_basebackup, без SUPERUSER.
3. Разграничение доступа к каталогу копий: права 600 владельцу backup, доступ в облачное хранилище по отдельному ключу только на запись для сервера и только на чтение для администратора.
4. Хранение копий вне основного сервера и неизменяемое хранение (object lock / WORM), чтобы шифровальщик или скомпрометированная учётная запись не удалили копии.
5. Контроль целостности: вычисление sha256 при создании, проверка при копировании и перед восстановлением; pg_restore -l как быстрая проверка читаемости архива.
6. Регулярное автоматическое тестовое восстановление в изолированную базу с проверкой COUNT и JOIN, как в задании 3.
7. Журналирование и оповещение: лог каждого запуска резервного копирования, алерт при ошибке или отсутствии свежей копии.

## Контрольные вопросы

1. Резервная копия это сохранённая копия данных и структуры базы, из которой можно восстановить базу после потери или повреждения.
2. pg_dump создаёт логическую копию одной базы данных в виде SQL-скрипта или архива.
3. Логическое копирование сохраняет SQL-описание объектов и данные (независимо от версии и платформы, медленнее, можно выбирать объекты). Физическое копирует файлы каталога данных как есть (быстро, весь кластер, та же версия и платформа, нужно для PITR).
4. pg_restore восстанавливает базу из архивных форматов pg_dump (custom, directory, tar), позволяет выбирать объекты и восстанавливать параллельно.
5. Форматы pg_dump: plain (p, SQL-текст), custom (c), directory (d), tar (t).
6. Восстановление в отдельную базу не затрагивает рабочую: если копия повреждена или неполна, рабочие данные не пострадают, а восстановленную базу можно проверить и сравнить с исходной.
7. Сравнить количество строк в таблицах, наличие всех таблиц, выполнить JOIN для проверки связей, проверить ограничения и последовательности, сверить контрольные выборки с исходной базой.
8. pg_dumpall это утилита логической копии всего кластера: всех баз, ролей и табличных пространств, в SQL-формате.
9. pg_basebackup делает физическую копию кластера с работающего сервера, используется для PITR и создания реплик.
10. WAL (Write-Ahead Log) это журнал упреждающей записи: все изменения сначала пишутся в журнал, затем в файлы данных. Обеспечивает восстановление после сбоя, репликацию и PITR.
11. PITR (Point-In-Time Recovery) это восстановление базы на заданный момент времени из базовой копии и архива WAL, например на момент перед ошибочным DELETE.
12. Правило 3-2-1: три копии данных, на двух разных типах носителей или независимых системах, одна копия вне основной площадки.
13. Копии содержат все данные в открытом виде и часто покидают защищённый периметр (облако, внешние диски). Шифрование защищает от чтения при краже или утечке файла.
14. RPO это максимально допустимый объём потерянных данных во времени, то есть насколько старой может быть последняя копия.
15. RTO это максимально допустимое время простоя до полного восстановления работы системы.
16. Копия может быть повреждена, неполна, несовместима с версией или не иметь ключа; процедура восстановления может быть не отработана. Только регулярный тест доказывает, что копия пригодна и RTO выполним.
17. При отказе диска, пожаре, краже сервера, вирусе-шифровальщике или ошибке администратора (rm -rf) копия погибает вместе с базой. Также взломавший сервер получает и базу, и все копии.

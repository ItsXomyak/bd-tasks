# Практическое занятие № 8. Шифрование данных в PostgreSQL с pgcrypto

Цель: получить навыки шифрования и расшифрования конфиденциальных данных в PostgreSQL, изучить расширение pgcrypto и определить требования к безопасному хранению ключей.

Среда: PostgreSQL 16 в Docker, база university, pgcrypto 1.3, клиент psql.

## Этап 1. Открытое хранение

```sql
CREATE TABLE students_security (
    id SERIAL PRIMARY KEY,
    student_name TEXT NOT NULL,
    document_number TEXT NOT NULL
);

INSERT INTO students_security (student_name, document_number) VALUES
    ('Иван Петров', 'DOC-1001'),
    ('Анна Сидорова', 'DOC-1002'),
    ('Алексей Смирнов', 'DOC-1003');

SELECT * FROM students_security;
```

Результат: 3 строки, номера документов видны как есть.

Почему это риск. Номер документа это персональные данные. Любой, кто получит SELECT на таблицу, дамп базы, резервную копию или файл логов с этим запросом, сразу читает номера. Утечка не требует никаких дополнительных усилий.

## Этап 2. Подключение pgcrypto

```sql
CREATE EXTENSION IF NOT EXISTS pgcrypto;

SELECT encode(pgp_sym_encrypt('TEST-123', 'class-demo-key'), 'hex') AS encrypted_value;
```

Расширение подключилось, версия 1.3. Результат функции:

```
c30d040703026915909f8fc75c0974d239011b1dca1d365997b84556cdaa4b47980ca3ce5bbb69...
```

Почему значение отличается от TEST-123. Функция прогнала строку через симметричный шифр по стандарту OpenPGP с ключом, выведенным из парольной фразы. На выходе двоичный пакет: заголовок, случайная соль, зашифрованные данные. Он длиннее исходной строки и без ключа не читается. Повторный вызов с теми же аргументами дал другой hex, потому что соль генерируется заново при каждом шифровании.

## Этап 3. Зашифрованное хранение

```sql
CREATE TABLE students_encrypted (
    id SERIAL PRIMARY KEY,
    student_name TEXT NOT NULL,
    encrypted_document BYTEA NOT NULL
);

INSERT INTO students_encrypted (student_name, encrypted_document) VALUES
    ('Иван Петров', pgp_sym_encrypt('DOC-1001', 'class-demo-key')),
    ('Анна Сидорова', pgp_sym_encrypt('DOC-1002', 'class-demo-key')),
    ('Алексей Смирнов', pgp_sym_encrypt('DOC-1003', 'class-demo-key'));

SELECT id, student_name, encode(encrypted_document, 'hex') AS encrypted_value
FROM students_encrypted;
```

В столбце encrypted_value вместо DOC-1001 лежит hex-строка на 74 байта вида c30d040703023a0bcf687dc9ab6d7f... По ней нельзя понять ни сам номер, ни его длину, ни что у трёх строк одинаковый префикс DOC-. Открытое хранение отдаёт значение сразу, зашифрованное требует ключ.

## Этап 4. Расшифрование

```sql
SELECT id, student_name, pgp_sym_decrypt(encrypted_document, 'class-demo-key') AS document_number
FROM students_encrypted;
```

Результат: DOC-1001, DOC-1002, DOC-1003. Исходные значения восстановлены верно.

```sql
SELECT pgp_sym_decrypt(encrypted_document, 'incorrect-demo-key') FROM students_encrypted;
```

Результат: ERROR: Wrong key or corrupt data.

Ответы:

1. Успешное расшифрование с правильной фразой вернуло все три номера без искажений.
2. Почему нужна правильная фраза. Из фразы выводится ключ шифра. С другой фразой получается другой ключ, расшифрованные байты не проходят проверку целостности внутри пакета OpenPGP, и функция отказывает. Без фразы данные математически не восстанавливаются.
3. Последствия потери ключа. Зашифрованные данные превращаются в мусор навсегда, их не вернёт ни администратор, ни резервная копия. Для университета это потеря номеров документов всех студентов.
4. Почему нельзя хранить фразу рядом с данными. Если фраза лежит в той же базе, в том же дампе или в коде рядом с запросом, то любой, кто получил таблицу, получил и ключ. Шифрование становится декоративным.

## Этап 5. Сравнение способов хранения

Критерий — открытое хранение — шифрование полей

- Читаемость значения прямо в таблице — да, видно сразу — нет, hex-мусор
- Возможность восстановить исходное значение — всегда — только с правильным ключом
- Необходимость защищать ключ — нет ключа — да, ключ становится главным секретом
- Последствия утечки таблицы — все номера скомпрометированы — злоумышленник получает шифротекст, без ключа бесполезный
- Удобство поиска по значению — WHERE document_number = ..., работает индекс — нужно расшифровывать каждую строку; сравнение шифротекстов напрямую не работает из-за случайной соли (проверил: count = 0)

Достаточно ли шифрования отдельных полей? Нет. Шифрование закрывает только одну угрозу: чтение данных из таблицы или дампа без ключа. Остаются:

- Права доступа. Если у роли есть SELECT и она знает ключ (или ключ зашит в функцию/представление), она читает всё. Нужны минимальные привилегии, RLS, отдельные роли без доступа к расшифровке.
- Безопасность приложения. SQL-инъекция или утечка ключа из кода приложения обходит шифрование. Приложение должно ходить под ограниченной учёткой и держать ключ вне кода.
- Хранение ключей. Ключ в SQL-запросе, в логах, в репозитории равен отсутствию шифрования. Нужен внешний менеджер секретов, ротация, ограниченный доступ.
- Расшифрованные данные в памяти, логах, результатах запросов тоже нужно защищать.

## Этап 6. Проектирование защиты ключей

Ситуация: фраза записана в SQL-запросе, приложение работает с расширенными правами.

Риск — последствия — мера

- Ключ в исходном коде — попадает в git, в логи, к любому разработчику и в утечку репозитория; данные расшифровывает кто угодно — хранить в переменной окружения или менеджере секретов (Vault, KMS), в коде только ссылка; ротация при смене команды
- Приложение имеет избыточные права — через инъекцию или баг можно менять, удалять таблицы, читать чужие данные, создавать роли — отдельная роль с минимальными правами: SELECT/INSERT на нужные таблицы, без DDL и CREATEROLE; расшифровку выносить в функцию с SECURITY DEFINER и давать EXECUTE только тем, кому положено
- Резервная копия не зашифрована — дамп содержит шифротекст, а если ключ рядом (в коде, в той же базе), то бэкап равен открытым данным; кража носителя или бакета — шифровать бэкапы, хранить отдельно от ключей, ограничивать доступ, проверять восстановление
- Ключ потерян или скомпрометирован — потерян: данные невосстановимы; скомпрометирован: все записи читаются — резервные копии ключа в защищённом хранилище, процедура ротации с перешифровкой данных новым ключом, версионирование ключей, аудит доступа
- Расшифрованные данные попадают в логи — логи SQL, логи приложения, трассировки содержат номера в открытом виде и лежат без защиты — не логировать параметры запросов и результаты, маскировать чувствительные поля, ограничивать доступ к логам, не выводить ключи в сообщения об ошибках

## Контрольные вопросы

1. Шифрование данных это преобразование открытого текста в шифротекст с помощью алгоритма и ключа так, что прочитать его можно только обратным преобразованием с тем же (или парным) ключом.
2. Открытый текст читается напрямую. Шифротекст это набор байтов, который без ключа не раскрывает ни содержимое, ни структуру.
3. pgcrypto даёт в PostgreSQL криптографические функции: хеширование, симметричное и асимметричное шифрование OpenPGP, генерацию случайных байтов. Позволяет шифровать прямо в SQL.
4. pgp_sym_encrypt шифрует данные симметричным шифром по парольной фразе и возвращает BYTEA-пакет OpenPGP.
5. pgp_sym_decrypt расшифровывает такой пакет по той же парольной фразе и возвращает исходный текст; при неверной фразе выдаёт ошибку.
6. BYTEA хранит произвольные двоичные данные. Шифротекст это байты, а не текст, в TEXT его класть нельзя из-за кодировок и нулевых байтов.
7. Из парольной фразы выводится ключ шифра. Другая фраза даёт другой ключ, данные не расшифровываются и не проходят проверку целостности.
8. Шифрование обратимо: с ключом возвращаем исходное значение. Хеширование необратимо: из хеша исходное значение не получить, оно подходит для паролей и проверки целостности, но не для данных, которые нужно читать.
9. Код попадает в репозиторий, логи сборки, к разработчикам и в утечки. Ключ в коде равен ключу у всех, кто видел код. Смена ключа требует переписывания кода.
10. Минимальные права ролей и приложения, RLS, хранение ключей вне базы и кода, шифрование и защита резервных копий, ротация ключей, запрет записи секретов и расшифрованных значений в логи, аудит доступа, параметризованные запросы против инъекций.

## Вывод

pgcrypto позволяет зашифровать отдельное поле одной функцией и так же просто расшифровать его при наличии ключа. В таблице вместо номеров документов лежат 74 байта мусора, неверный ключ даёт ошибку, правильный возвращает исходные значения. Цена: поиск по зашифрованному полю не работает через индекс, а вся безопасность переезжает в ключ. Если ключ лежит в коде рядом с запросом или приложение работает с правами админа, шифрование не защищает ничего. Шифрование полей это один слой; вместе с ним нужны минимальные привилегии, защищённое хранение и ротация ключей, шифрованные бэкапы и чистые логи.

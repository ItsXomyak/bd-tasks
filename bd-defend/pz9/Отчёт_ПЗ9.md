# Практическая работа № 9. Настройка защищённого подключения к базе данных. Проверка соединения по TLS

Цель: научиться проверять защищённость соединения с PostgreSQL, анализировать параметры TLS, проверять сертификаты и определять, используется ли шифрование.

Среда: PostgreSQL 16 в Docker, база university, клиент psql внутри контейнера. Для сервера сгенерирован самоподписанный сертификат CN=localhost (certs/server.crt, certs/server.key), при первом старте он копируется в PGDATA и выполняется ALTER SYSTEM SET ssl = on.

## Задание 1. Проверка настроек SSL/TLS сервера

```sql
SHOW ssl;
SHOW config_file;
SHOW hba_file;
```

Результат:

- ssl = on, поддержка TLS включена
- config_file = /var/lib/postgresql/data/postgresql.conf
- hba_file = /var/lib/postgresql/data/pg_hba.conf
- ssl_cert_file = server.crt, ssl_key_file = server.key (пути относительно каталога данных)

Назначение файлов:

- postgresql.conf — основные параметры сервера: порт, адреса прослушивания, память, логирование, параметры TLS (ssl, ssl_cert_file, ssl_key_file, ssl_ca_file, ssl_min_protocol_version).
- pg_hba.conf — правила аутентификации клиентов: кто (пользователь), куда (база), откуда (адрес), каким способом (TCP с TLS или без, unix-сокет) и каким методом (scram-sha-256, cert, trust и т.д.) может подключаться.

Вопрос: достаточно ли ssl = on, чтобы гарантировать, что конкретный клиент подключился по TLS?

Нет. ssl = on означает только, что сервер готов принимать TLS-соединения. Клиент с sslmode=disable или prefer при ошибке TLS подключится без шифрования, и сервер это разрешит, если в pg_hba.conf есть правило host (а не hostssl). Подключение через unix-сокет тоже идёт без TLS. Факт шифрования конкретной сессии проверяется только через pg_stat_ssl, а запрет нешифрованных подключений обеспечивается правилами hostssl / hostnossl в pg_hba.conf.

## Задание 2. Проверка текущего соединения по TLS

```sql
SELECT a.pid, a.usename, a.datname, a.client_addr, s.ssl, s.version, s.cipher, s.bits
FROM pg_stat_activity AS a
JOIN pg_stat_ssl AS s ON a.pid = s.pid
WHERE a.pid = pg_backend_pid();
```

Результат для psql, запущенного внутри контейнера (unix-сокет):

```
 pid | usename  |  datname   | client_addr | ssl | version | cipher | bits
  81 | postgres | university |             | f   |         |        |
```

ssl = false, зафиксировано: локальное соединение через сокет не шифруется.

Тот же запрос по TCP с sslmode=disable:

```
 pid | client_addr | ssl | version | cipher | bits
  84 | ::1         | f   |         |        |
```

Тот же запрос по TCP с sslmode=require:

```
 pid | client_addr | ssl | version |         cipher         | bits
  87 | ::1         | t   | TLSv1.3 | TLS_AES_256_GCM_SHA384 |  256
```

Ответы:

1. В исходном соединении (unix-сокет) TLS не используется. При подключении по TCP с sslmode=require TLS используется.
2. Версия протокола: TLSv1.3.
3. Шифр: TLS_AES_256_GCM_SHA384, длина ключа 256 бит.
4. Успешное подключение ничего не говорит о защите канала: сервер с ssl = on и правилом host принимает и шифрованные, и открытые соединения. Один и тот же сервер в нашем опыте дал ssl = f и ssl = t в зависимости от настроек клиента. Кроме того, sslmode=require шифрует канал, но не проверяет, кому принадлежит сертификат, поэтому не защищает от подмены сервера.

## Задание 3. Анализ режимов sslmode

- Пример A: sslmode=disable
- Пример B: sslmode=require
- Пример C: sslmode=verify-full + sslrootcert

Таблица:

```
Критерий                                            | A disable | B require | C verify-full
Требуется шифрование                                | нет       | да        | да
Проверяется доверенная цепочка сертификата          | нет       | нет       | да
Проверяется имя сервера                             | нет       | нет       | да
Подходит для защищённого подключения в production   | нет       | нет       | да
```

Примечание по B: require проверяет цепочку только если у клиента есть файл root.crt, по умолчанию его нет, поэтому принимается любой сертификат.

Проверка на стенде:

```
verify-full, host=localhost, sslrootcert=/certs/server.crt   -> ssl = t, TLSv1.3
verify-full, host=127.0.0.1                                   -> server certificate for "localhost" does not match host name "127.0.0.1"
verify-ca без sslrootcert                                     -> root certificate file "/root/.postgresql/root.crt" does not exist
```

Почему verify-full предпочтительнее. require защищает только от пассивного прослушивания: трафик зашифрован, но клиент примет сертификат любого сервера, в том числе злоумышленника, вставшего посередине (MITM). verify-ca проверяет, что сертификат выдан доверенным CA, но не проверяет имя, поэтому любой сертификат этого CA подойдёт. verify-full проверяет и цепочку доверия, и совпадение имени хоста с CN/SAN сертификата, то есть подтверждает, что клиент подключился именно к нужному серверу. Это единственный режим, дающий аутентификацию сервера.

## Задание 4. Анализ правил доступа pg_hba.conf

Правило:

```
hostssl university app_user 10.10.10.0/24 scram-sha-256
```

- hostssl — только TCP/IP-подключения с TLS
- university — база данных
- app_user — пользователь
- 10.10.10.0/24 — адреса клиентов 10.10.10.0 – 10.10.10.255
- scram-sha-256 — метод парольной аутентификации

На стенде правило добавлено первой строкой, вывод pg_hba_file_rules:

```
 line_number |  type   |   database    | user_name  |  address   |    netmask      |  auth_method
           1 | hostssl | {university}  | {app_user} | 10.10.10.0 | 255.255.255.0   | scram-sha-256
         118 | local   | {all}         | {all}      |            |                 | trust
         120 | host    | {all}         | {all}      | 127.0.0.1  | 255.255.255.255 | trust
         122 | host    | {all}         | {all}      | ::1        | ffff:...:ffff   | trust
         129 | host    | {all}         | {all}      | all        |                 | scram-sha-256
```

Ответы:

1. Правилу соответствует клиент, который одновременно: подключается по TCP с TLS, к базе university, под пользователем app_user, с адреса из 10.10.10.0/24, и знает пароль (SCRAM). Любое несовпадение, и правило пропускается, поиск идёт дальше по файлу.
2. hostssl срабатывает только для TLS-соединений. Если для пользователя/сети есть только hostssl-правила (и нет host), нешифрованное подключение не найдёт подходящего правила и будет отклонено. Так сервер принудительно требует TLS, независимо от того, что указал клиент в sslmode.
3. pg_hba.conf читается сверху вниз, применяется первое совпавшее правило. В нашем стенде строка 129 host all all all scram-sha-256 разрешает тому же app_user подключиться без TLS с любого адреса, то есть hostssl в первой строке ничего не ограничивает. Нужно проверять все правила, их порядок и убирать широкие host all all all.
4. Дополнительные способы защиты:
   - аутентификация по клиентскому сертификату (auth_method cert или clientcert=verify-full) — вход только с выданным сертификатом
   - правило hostnossl all all all reject явным запретом нешифрованных подключений
   - ограничить listen_addresses и закрыть порт 5432 межсетевым экраном для всех, кроме серверов приложений
   - ssl_min_protocol_version = TLSv1.2 и отключение слабых шифров

## Задание 5. Схема защищённого подключения

План для информационной системы университета с персональными данными студентов:

1. На сервере ssl = on в postgresql.conf.
2. Сервер использует сертификат, выданный на имя db.university.example внутренним или публичным CA, и соответствующий закрытый ключ (server.key, права 0600, владелец postgres).
3. На клиенте установлен корневой сертификат этого CA (root.crt), клиент доверяет только ему.
4. В строке подключения приложения sslmode=verify-full и sslrootcert=/path/to/root.crt.
5. host в строке подключения совпадает с CN/SAN сертификата сервера (db.university.example, не IP-адрес).
6. В pg_hba.conf только правила hostssl для нужных пользователей, баз и подсетей; host all all all удалён; при необходимости hostnossl all all all reject.
7. Для приложения создана отдельная учётная запись app_user с минимальными правами (CONNECT на базу, SELECT/INSERT только на нужные таблицы), без SUPERUSER и CREATEDB.
8. Порт 5432 открыт в межсетевом экране только для подсети серверов приложений.
9. Контроль срока действия сертификатов (мониторинг notAfter) и их плановая замена до истечения; после замены SELECT pg_reload_conf().

Клиентская конфигурация:

```
host=db.university.example
port=5432
dbname=university
user=app_user
sslmode=verify-full
sslrootcert=/path/to/root.crt
```

Схема подключения:

Клиент приложения → проверка сертификата сервера (цепочка до root.crt и совпадение имени db.university.example) → защищённое TLS-соединение (TLSv1.3) → аутентификация пользователя PostgreSQL (правило hostssl + scram-sha-256) → проверка прав доступа (GRANT на таблицы для app_user) → работа с базой данных.

## Выводы

- ssl = on включает поддержку TLS, но не заставляет клиентов его использовать; на одном сервере получены соединения с ssl = f и ssl = t.
- Факт шифрования сессии проверяется через pg_stat_ssl (ssl, version, cipher, bits).
- Только sslmode=verify-full проверяет и цепочку доверия, и имя сервера; require и verify-ca уязвимы к подмене сервера.
- Принудительный TLS на стороне сервера обеспечивается правилами hostssl в pg_hba.conf при условии, что более широких host-правил ниже нет.
